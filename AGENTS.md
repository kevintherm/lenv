# lenv: project memory

Read this file before working on lenv. Update it when the owner makes a decision, a milestone changes, or work is handed off. Keep proposals separate from decisions. Record which checks ran and on which platforms; don't mark unverified work complete.

## Project

lenv is a lightweight local development environment manager inspired by Laragon and FlyEnv. A developer should be able to pick a service version, install it, group it with other project services, and open a local site over HTTPS. The same work must be possible from the CLI without a GUI.

Repository: <https://github.com/kevintherm/lenv.git>

## Owner decisions

- Target macOS and Linux. Develop on macOS first; defer live Linux verification so it doesn't block macOS development. Windows can wait.
- Support headless and desktop operation. The public command is `lenv`; use `lenv daemon` for the daemon rather than a separate `lenvd` command. The daemon monitors and manages services. Reuse proven supervision where practical instead of writing a new supervisor.
- Organize commands under named areas. Use `lenv service <service> <action>` for service commands, such as `lenv service postgres list` and `lenv service postgres install <version>`. Reserve `lenv group <action>` for project groups, starting with `lenv group create <name>` when groups are implemented.
- Keep the footprint small and the headless install standalone. The GUI is a simple service control surface. Evaluate Gio and `gogpu/ui`; neither is selected. FLTK and Qt were earlier suggestions, not commitments.
- Keep lenv-installed services separate from services installed outside lenv. Discover external services without taking control. Offer explicit opt-in to control an existing service, such as a user's PostgreSQL or Redis installation.
- Make version selection and installation straightforward from the GUI. Let power users add their own package sources.
- Use prebuilt archives from an upstream publisher for the first managed packages. Pin and verify downloads and keep them in lenv's own store. Do not require Homebrew to install or run a managed package; keep the option to bring your own binaries.
- Expand the managed catalog before the desktop prototype. The baseline is PostgreSQL, MySQL, MariaDB, MongoDB, Redis, Caddy, PHP, and Node.js. This is a target list, not a list of packages already available.
- The owner approved publishing and maintaining lenv-built Apple Silicon packages for Redis and MariaDB. Review redistribution requirements before publishing.
- The owner approved the full lenv source for the first public commit. Keep compiled binaries and local state out of Git.
- Keep Laragon-style isolation and flexibility. Project groups, pretty local URLs (sites), and automatic local HTTPS are early priorities.
- Run development and test commands directly. Bring product or architecture tradeoffs to the owner for a decision rather than asking them to run routine commands.
- Keep application logic separate from CLI, IPC, and platform details. Run tests locally for now; defer GitHub Actions.

## Architecture boundaries

- `cmd/lenv` parses arguments and renders output. The GUI should use the same daemon API. Neither client should call package managers or supervisors directly.
- `internal/daemon` handles local HTTP requests and delegates to application packages. Keep lifecycle, ownership, and group rules out of request handlers.
- `internal/packages` owns version selection, verification, extraction, and the package store. It does not start services. `internal/discovery` inventories binaries and service registrations without taking control.
- `internal/linked` owns external opt-in and lifecycle checks. It keeps links separate from managed instances and delegates control to the external manager. Discovery only uses the read-only Homebrew listing.
- `internal/sites` validates site inputs, manages the optional Caddy process, and keeps its CA in private state. CLI and GUI clients use the daemon API rather than invoking Caddy.
- Keep platform calls at adapter boundaries, such as `internal/postgres/launchd.go`. Introduce small interfaces where a second platform or test substitute needs them. Don't add layers that only pass calls through.
- For future groups, compose start/stop/status operations through instance management rather than calling launchd or systemd directly.

## Verification

Run `go test -race ./...` and `go vet ./...` locally. Use fixtures for archive handling and platform output, and temporary sockets and state directories for live smoke tests. When CI is needed, add a GitHub Actions workflow that runs the fixture-based suite and vet on macOS and Linux. Keep live supervisor tests separate so routine CI does not require a logged-in desktop or systemd user session.

## Proposed architecture

- A Go CLI and daemon share one headless binary. The optional GUI and CLI use the same local API over a private Unix socket. The GUI does not own service lifecycles.
- Use launchd on macOS and systemd user units on Linux to supervise lenv-owned instances. Keep package installation, instance configuration, readiness, and group orchestration in lenv. Decide separately whether boot without a login or survival after logout is required.
- Track packages, service instances, and external service registrations separately. A binary path does not identify a running instance. Linking an external service should delegate to its existing manager, such as Homebrew Services or systemd, without moving data, rewriting configuration, or taking ownership of upgrades. Unlinking should leave it untouched. Unsupported managers stay read-only.
- Use one declarative package format for the default catalog and custom sources. Pin and verify artifacts. Keep installed binaries separate from per-instance data, configuration, logs, and ports so groups can run the same version side by side. This is project isolation, not a security sandbox.
- Let groups start their owned instances in order and stop them in reverse. Detect port conflicts before startup. Don't stop linked or shared services on group shutdown by default.
- Try one optional, loopback-only Caddy proxy for sites and local TLS. Start with `.localhost` names, make local CA trust explicit and reversible, and allow a high-port fallback when `443` is unavailable. Don't run the daemon as root for this.
- Compare Gio and `gogpu/ui` using the same small GUI workflow. Measure shipped size and idle memory, and check keyboard, screen-reader, and Linux compatibility before choosing.

## Prior research

- Laragon uses an editable [`usr/packages.conf`](https://github.com/leokhoa/laragon/blob/master/usr/packages.conf) for [Quick Add](https://laragon.org/docs/quick-add). It picks up compatible builds placed in its own `bin` tree and manages processes itself, not through Windows Services. Its [Procfile](https://laragon.org/docs/procfile) supports custom commands, working directories, environment files, and autostart. The public repo does not expose the internals of `laragon.exe`.
- FlyEnv's catalog varies by service and OS. [PostgreSQL](https://flyenv.com/features/postgresql) and [Redis](https://flyenv.com/features/redis) use Homebrew on macOS/Linux and MacPorts on macOS; some other modules offer direct archives on those platforms. Its [scanner](https://github.com/xpf0000/FlyEnv/blob/a158622d3c67da46739ce5115422017b6bcf52ef/src/fork/util/Version.ts#L354-L498) finds known binaries in its own store, package-manager paths, system paths, and user-added folders. The modules reviewed launch and track their own instances rather than link to an external service job. Its [Startup Groups](https://flyenv.com/features/startup-groups) start in order and stop in reverse. Research was based on docs and source, not running either product.

## Progress and milestones

1. **Headless read-only discovery: implemented; Linux runtime verification pending.** `cmd/lenv` provides `lenv daemon`, `lenv status` (also `lenv daemon status`), and `lenv discover`. `internal/daemon` serves the versioned local API over a private Unix socket and handles shutdown and stale sockets. `internal/discovery` lists PostgreSQL and Redis executable paths without running the candidates. It reports Homebrew or systemd registrations separately and supports extra scan directories. Discovery itself performs no install or service-control operations. See `README.md` for usage.
   - macOS arm64: `go test ./...`, `go test -race ./...`, and `go vet ./...` passed. A real CLI smoke test found local Homebrew binaries and an added test binary without executing it, checked daemon status, and confirmed socket cleanup on shutdown. The host had no matching registered Homebrew services, so tests with fixtures cover registered and running entries.
   - Linux: Go builds passed for amd64 and arm64 with `CGO_ENABLED=0`. Fixtures cover systemd unit parsing, state, and an unavailable user bus. Live systemd verification is deferred, not waived. Repeat the daemon/CLI smoke test on a Linux host with systemd and compare results against its user and system service inventories before marking the cross-platform milestone complete. Continue macOS work in the meantime.
2. **Managed install and lifecycle verified on Apple Silicon; Homebrew linking implemented, live start/stop verification pending.** `lenv service postgres list` lists catalog entries for the current platform. `lenv service postgres install 16.16` verifies and installs the pinned archive into the private package store; a repeat install reuses it. `lenv service postgres init --version 16.16` uses the store. `--bin-dir` still accepts trusted PostgreSQL binaries from outside lenv. `init/start/stop/status/logs` use the daemon API and a per-instance launchd job in the current login session. Each instance has separate data, logs, and credentials. It binds only to IPv4 loopback, and `stop` unregisters the job without deleting data.
   - macOS arm64 with Homebrew PostgreSQL 16: live smoke passed for initialization, duplicate-name and occupied-port protection, authenticated SQL, log output, surviving a daemon restart with the same PostgreSQL PID, launchd recovery after killing only the test PostgreSQL process, and intentional stop with an open SQL session. The test used a separate temporary socket and state directory. `go test -race ./...` and `go vet ./...` passed; Linux amd64 and arm64 cross-builds passed.
   - The first catalog entry is the [Theseus PostgreSQL 16.16 Apple Silicon archive](https://github.com/theseus-rs/postgresql-binaries/releases/tag/16.16.0), 89 MB compressed and about 262 MB of unpacked files. The live install downloaded it into a temporary store, reused it on repeat install, initialized a cluster, verified authenticated SQL and logs, and stopped it with Homebrew absent from `PATH`. `otool` confirmed the tested executables and their dependent libraries referenced only the bundle or macOS system libraries. Unit tests cover checksum rejection, confined archive extraction, and cleanup after failed installs. Race tests, vet, and Linux cross-builds passed after adding the installer. Intel macOS and Linux do not yet have a managed catalog entry.
   - After grouping the CLI under `service`, a live macOS smoke test confirmed `list` → `install` → `list` against a temporary store. Race tests and vet passed. The daemon API and stored data paths did not change.
   - User-registered Homebrew PostgreSQL services can be linked and unlinked explicitly; `start`, `stop`, and `status` require `--linked` to target one. Start loads the existing service file through Homebrew; stop keeps the login registration. Fixtures verify delegated commands, link persistence, refusal of unsupported or changed registrations, and that unlink does not call Homebrew. A live macOS arm64 CLI/daemon smoke confirmed discovery and rejected link/control requests left the host's unregistered Homebrew PostgreSQL unchanged. Live start/stop and unlink-while-running still need an isolated registered service; the host had none. Race tests, vet, and both Linux cross-builds passed.
3. **Project groups and the first local HTTPS route verified on macOS arm64.** `lenv group create/add/remove/start/stop/status` persists groups in private state and composes lifecycle through managed PostgreSQL. Membership is exclusive; linked Homebrew services are not eligible. Start checks ports before starting members in order; stop runs in reverse, and remove does not stop the instance. Start failures after preflight can leave some members running.
   - Live macOS smoke ran two groups with three temporary clusters on separate ports and authenticated SQL in each. An occupied port blocked startup before any member started. Stopping the first group and detaching the second group's member left the latter's PID unchanged. Definitions survived a daemon restart. Race tests, vet, and Linux amd64/arm64 cross-builds passed; live Linux lifecycle remains deferred.
   - `lenv site start NAME PORT`, `status`, and `stop` manage one optional `.localhost` HTTPS route with Caddy on the daemon's `PATH` or an installed Caddy selected by `--version`. The proxy defaults to IPv4 loopback on port 8443; `LENV_HTTPS_PORT` overrides it. It never installs trust, does not run the upstream app, and does not restore the route on restart. The private CA is reused.
   - Live macOS arm64 smoke with Caddy 2.11.9 verified the occupied-port error, forwarding over HTTPS with the private CA, failure without trust, an unmatched HTTP/1.1 Host rejected, an IPv4 loopback-only listener, CA reuse, and stopping the proxy without stopping the app. Normal daemon shutdown closed the listener. No browser trust store changes were tested or made. Race tests, vet, and both Linux cross-builds passed; live Linux sites are unverified.
4. **Baseline catalog expansion: seven of eight installable on Apple Silicon.** One shared installer covers PostgreSQL 16.16/17.12, MySQL 8.4.10, MongoDB Community Server 8.0.38, Redis 8.12.0 core, Caddy 2.11.9, PHP 8.5.12 CLI, and Node.js 24.22.3 LTS. The PostgreSQL store path and old API endpoint still work. MySQL, MongoDB, Redis, PHP, and Node.js are package-only; PostgreSQL retains full lifecycle and Caddy can run the site proxy. No Intel Mac or Linux artifacts are enabled.
   - On macOS arm64 with Homebrew off `PATH`, live CLI tests verified downloading, reusing, and running each new package in temporary state. PostgreSQL 17.12 passed authenticated SQL and clean stop; installed Caddy proxied HTTPS without Caddy on `PATH`; Node's npm, MySQL's client, and PHP CLI execution also passed. PHP has `pdo_mysql` and `pgsql` but not `pdo_pgsql`. MySQL and MongoDB instance lifecycle was not tested. Race tests, vet, and Linux amd64/arm64 cross-builds passed.
   - Redis server releases did not provide a standalone Apple Silicon archive; the Redis Stack macOS cask declares Homebrew dependencies. MariaDB's current official catalog did not include macOS tarballs, and the third-party SnapDBApp builds checked were not current stable patches.
   - Follow-up source review found the Redis 8.12.0 cask also declares Homebrew dependencies, and pkgx builds for both databases depend on pkgx libraries. Local [candidate build recipes](contrib/package-builds/README.md) do not change the catalog or publish anything. Redis 8.12.0 core (no TLS or optional modules) built on Apple Silicon with Homebrew off `PATH`. Both binaries link only macOS system libraries; loopback authentication and read/write, clean stop, and persistence after restart passed. The private Unix-socket smoke also passed.
   - Both original candidates passed lenv's archive extractor. MariaDB 11.8.9 built with pinned static OpenSSL. The relocated build passed socket SQL, clean stop, and restart persistence on macOS arm64 with Homebrew off `PATH`; `otool` found no unsupported absolute library references across its 95 Mach-O files. That build is not for publication: GPLv2 redistribution of the static OpenSSL combination has not been verified. The replacement recipe uses bundled wolfSSL for the server and disables client TLS. Its build, archive, and runtime checks are pending.
   - [Redis 8.12.0 core](https://github.com/kevintherm/lenv/releases/tag/pkg-redis-8.12.0-darwin-arm64-r1) is published with corresponding source and SHA-256 sums. Both public downloads matched. On macOS arm64, the CLI downloaded, installed, and reused the pinned archive with Homebrew off `PATH`, and the installed binaries passed the socket smoke test. GitHub release immutability is off; the catalog pins the released bytes, and any rebuilt package must use a new tag.
